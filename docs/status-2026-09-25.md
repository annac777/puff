## What changed technically

**Work outside the browser now counts.** The advisor's critique was that the second step —
noticing the natural pause — only works inside the browser, so for someone in VS Code or Word,
Puff either waits forever or falls back to the fixed timer it was designed to beat.

It was worse than that. The first step was broken too: elapsed work time was also measured from
browser input alone, so forty minutes in a desktop editor accumulated **zero** active seconds.
Puff was silent, not wrong — which is harder to notice.

`chrome.idle` carries both halves system-wide. It reports on input across the whole machine, not
just the browser window.

| | In the browser | Outside it |
|---|---|---|
| Are they working | clicks, keys, scroll | `idle` state is `active` |
| Have their hands stopped | 10s of silence, and we can tell typing from scrolling | machine goes quiet, 15s floor |

Fifteen seconds is Chrome's minimum detection interval. It is the same *kind* of signal as the
in-browser pause, just coarser — and it is the only one of its kind that works in a desktop app.
So this is graceful degradation rather than a choice between scoping Puff to browser-only
workers and rebuilding it as a desktop app.

**Also shipped since the hackathon:** the rhythm model from Kaur et al. (CHI 2020) — Puff judges
the shape of recent work across short windows rather than one running total, and moves its own
threshold toward the moments this person actually accepts.

## The boundary that does not go away

**Puff can only hold a place that is a browser tab.** Working in VS Code, it can suggest a break
but cannot save where you were — it has no idea which file is open or where the cursor is.

That splits the product:

- **The invitation to stop** — works everywhere, via system-wide idle
- **Holding your place** — browser work only

The three-arm trial is unaffected, since the first two arms only need the invitation. But it is
a real limit on who the second half of the product serves, and the survey is measuring exactly
that (see below).

## Research

A screening survey is live, and an interview guide is written. Hyeji runs 3 interviews, Anna
runs 2.

The survey tests one hypothesis: *a break is easier to accept when the system first reduces the
cost of resuming*. It asks about specific recent occasions rather than preferences, because
people describe their habits as tidier than their habits are. The analysis plan — including the
exclusions and the go/no-go threshold — was written before any data arrived.

**The go/no-go:** if deep work turns out to happen mostly in desktop apps, "remembers your
place" serves a minority and the positioning has to lead with the invitation instead.

**Open question for the advisor:** this round is running as product research, which needs no IRB
review. NYU requires review *before* collection for student work intended for publication or
conference presentation, anonymous surveys included — and data gathered as product research
cannot be reclassified afterwards. If this is going toward a CHI Late-Breaking Work, is there an
existing protocol it could sit under, or should we file for exempt determination now?

## The trial

All three arms are buildable from the current code — the difference between them is one
parameter, not three implementations, which is what makes the comparison clean.

```
A   fires on a fixed timer              control
B   waits for the hands to stop         A vs B  — does timing matter
C   waits, and the pet asks             B vs C  — does the pet beat a dialog
```
